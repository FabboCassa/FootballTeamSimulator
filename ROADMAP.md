## Phase 1 — Domain & Match Engine v1
*Goal: a match can be simulated headless and the result is sensible.*

- [x] **1.1 Domain entities** — Player (attributes 1–100 per position role, age), Team, Squad, Club, Coach skeletons. Plain C#, serializable.
  ✅ Unit tests construct entities, round-trip serialize/deserialize.
- [x] **1.2 Player & league generation** — Seeded procedural generation: leagues of N clubs, squads of ~22 with realistic attribute/age/position distributions; name database.
  ✅ Test generates a 20-team league; histogram of attributes/ages matches expected curves (test asserts bounds).
- [x] **1.3 BalanceConfig** — All tunables in one JSON-loaded config object injected into every system.
  ✅ Changing a JSON value (e.g. home advantage) changes sim output; no tunables hard-coded (review).
- [x] **1.4 Match engine: result model** — Zone-based action resolution producing score + event timeline from lineups, attributes and a seed. No movement yet.
  ✅ Golden-master test: fixed seed ⇒ exact same report. 1,000-match harness: strong team beats weak ~70–80%, realistic score distribution (most common 1-0/1-1/2-1), no 15-0 outliers.
- [x] **1.5 Match engine: position stream** — Tick-based player/ball movement generation consistent with the event timeline (top-down coordinates).
  ✅ Test: ball position coincides with scorer's position at each goal tick; stream is deterministic per seed.
- [x] **1.6 Determinism cross-check** — Same sim run under .NET (server-like) and Unity IL2CPP.
  ✅ Identical MatchReport hash on both runtimes for 50 seeded matches.

- [x] **11.2 Scouting network: send scouts to areas, not to players** — Replace today's "tick a player and wait" model (5.4b) with a real scouting department.
  **Assignments:** a scout is sent to a **club**, a **nation**, or a **continent/region**, and works there continuously. The bigger the area, the LOWER the precision — a scout parked on one club learns its players fast and accurately; a scout covering South America returns a broad, vague shortlist. Precision should fall off with area size and rise with time spent, scout level and (later) the scout's familiarity with that area.
  **Discovery:** on an area assignment the scout **finds players himself** according to the **filters we give him** (role, age band, minimum ability/potential estimate, contract status, max value/wage, nationality). What comes back is a shortlist of candidates with the usual uncertainty ranges — the player never browses the whole database by hand.
  **Direct assignments:** the player can still point a scout at **named targets** — open a club, select the players he cares about, and put them under observation (today's behaviour, kept as the precise/expensive option).
  **Decisions to take with the user up front:** (a) do scouts become real entities with attributes (judging ability / judging potential / adaptability) and contracts, or stay an abstract department level as today? (b) does the assignment cost money (travel/wages) and is that the real limiter, or is it just the number of scouts? (c) how the shortlist is surfaced — a new "Rapporti" tab on the Osservatori screen, or into the Posta inbox as recurring reports? (d) does an area assignment also improve general **knowledge of that nation** (an FM-style per-area knowledge meter) that makes every future report there sharper?
  **Touches:** `Sim.Core/Scouting` (`ScoutingModel`, `KnowledgeStore`, `ScoutingAssignmentBook`, `ScoutingPolicy` — the assignment book already exists and is per-club, so area assignments are a natural extension), `ScoutingService`, the Osservatori screen, and `CareerState` (additive save bump for the assignments + filters).
